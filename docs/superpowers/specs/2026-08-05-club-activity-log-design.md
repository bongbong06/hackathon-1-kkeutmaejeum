# 동아리 활동 기록 관리 웹앱 — 설계 문서

- 작성일: 2026-08-05
- 팀: 1팀 / 끝맺음
- 팀원: 이봉운 (1인 팀)

## 1. 목적과 범위

동아리 임원이 동아리 활동 내역을 등록하고, 목록으로 확인하고, 삭제할 수 있는 웹앱을 만든다.
서버 없이 브라우저 localStorage만으로 동작하며, 파일 3개(`index.html` / `style.css` / `app.js`)로 구성한다.

구현 시간은 130분(14:00–16:10)이다. 이 제약이 아래 모든 결정의 기준이다.

### 구현 범위

필수 기능 (전 팀 공통)

1. 활동 등록 — 활동명, 날짜, 장소, 참여 인원, 메모
2. 활동 목록 조회 — 최신순 정렬, 빈 목록일 때 안내 문구
3. 활동 삭제 — 삭제 전 확인 절차

입력값 검증

- 활동명은 필수. 비어 있으면 저장하지 않는다
- 날짜는 미래 날짜를 입력할 수 없다
- 참여 인원은 1 이상의 정수

선택 기능 (3개)

1. 활동명·장소 키워드 검색
2. 반응형 레이아웃 (모바일 대응)
3. 주간 리캡 영상 — 활동 1건을 canvas 이미지 프레임 1장으로 만들고, 한 주치를 묶어 webm 영상 파일로 저장

### 범위에서 제외

- 서버, 데이터베이스, 빌드 도구
- 로그인 및 사용자 구분
- 활동 수정, 기간 필터, JSON 내보내기/가져오기 — 시간 제약으로 제외

## 2. 기술 스택

- HTML / CSS / JavaScript (프레임워크 없음)
- 저장소: 브라우저 localStorage
- 외부 라이브러리: 없음

선택 기능 3번(주간 리캡 영상)은 브라우저 내장 API인 `canvas`, `canvas.captureStream()`, `MediaRecorder`만 쓴다. 설치할 것도 CDN에서 받을 것도 없다.

원래는 로컬 AI 이미지 생성 모델로 활동 이미지를 만들 계획이었다. 명세에 이를 금지하는 조항은 없고 "담당 교수 판단에 따라 기술 스택은 대체할 수 있다"는 재량 조항도 있으나, 제출물이 강사가 클론해 여는 GitHub 저장소여서 모델과 로컬 서버가 없는 환경에서는 해당 기능이 동작하지 않는다. 파이프라인(활동 → 이미지 → 주간 영상)과 결과물은 그대로 두고 이미지 생성 주체만 canvas 렌더링으로 바꿨다.

## 3. 화면 구성

단일 페이지다. 데스크톱은 좌우 2단, 모바일은 1단으로 쌓인다.

```
[ 데스크톱 (>= 768px) ]                   [ 모바일 (< 768px) ]
+----------------------------------+     +--------------+
|      동아리 활동 기록 관리          |     |  헤더         |
+-------------+--------------------+     +--------------+
| 활동 등록    |  [검색어 입력]       |     | 등록 폼       |
| 활동명 *    | ------------------ |     +--------------+
| 날짜   *    |  활동 3건            |     | 월별 차트     |
| 장소        | +----------------+ |     +--------------+
| 인원   *    | | 신입생 환영회    | |     | 검색바        |
| 메모        | | 2026-03-02      | |     +--------------+
|  [ 저장 ]   | | 학생회관 · 24명  | |     | 목록          |
+-------------+ |        [삭제]   | |     +--------------+
| 월별 활동    | +----------------+ |
| 막대 차트    | +----------------+ |
+-------------+-+----------------+-+
```

- 빈 목록일 때는 목록 영역에 `아직 등록된 활동이 없습니다.` 를 표시한다
- 검색 결과가 없을 때는 `검색 결과가 없습니다.` 를 표시한다 (빈 목록과 구분한다)
- 목록 상단에 현재 표시 중인 활동 건수를 보여준다

## 4. 데이터 구조

`localStorage["activities"]`가 유일한 진실 소스다. 화면은 항상 여기서 다시 그린다.

활동 1건:

```js
{
  id,           // string. 고유 식별자
  title,        // string. 활동명 (필수)
  date,         // string. "YYYY-MM-DD"
  place,        // string. 장소
  memberCount,  // number. 참여 인원 (1 이상 정수)
  memo,         // string. 메모
  createdAt     // string. 등록 시각 ISO 문자열
}
```

- 배열 전체를 JSON 문자열로 직렬화해 한 번에 저장한다
- 정렬은 저장 시점이 아니라 화면에 그릴 때 `date` 기준 내림차순으로 한다

## 5. 데이터 흐름

단방향 흐름 하나로 통일한다.

```
사용자 입력
   -> activities 배열 변경
   -> saveActivities()
   -> render()
        +- renderList()   (검색어 필터 적용, 최신순 정렬)
        +- renderChart()  (월별 집계)
```

등록·삭제·검색 어디서든 `render()` 하나만 호출한다. 목록과 차트가 항상 같은 데이터를 보게 되므로 화면이 서로 어긋날 수 없다.

화면 상태는 두 가지뿐이다.

- `activities` — 활동 배열 (localStorage에서 읽어온 것)
- `searchKeyword` — 현재 검색어 (저장하지 않는다)

## 6. app.js 함수 구성

각 함수는 한 가지 일만 한다.

| 구분  | 함수                        | 하는 일                              |
| --- | ------------------------- | --------------------------------- |
| 저장소 | `loadActivities()`        | localStorage에서 배열을 읽는다. 실패하면 빈 배열 |
| 저장소 | `saveActivities()`        | 배열을 localStorage에 저장한다            |
| 검증  | `validateActivity(input)` | 검증 결과를 `{ ok, message }` 로 돌려준다   |
| 동작  | `handleSubmit(event)`     | 폼 제출을 받아 검증하고 추가한다                |
| 동작  | `handleDelete(id)`        | 확인을 거쳐 해당 활동을 삭제한다                |
| 조회  | `getFilteredActivities()` | 검색어를 적용하고 최신순으로 정렬해 돌려준다          |
| 화면  | `render()`                | 목록과 차트를 함께 다시 그린다                 |
| 화면  | `renderList()`            | 활동 목록을 그린다                        |
| 화면  | `renderChart()`           | 월별 활동 횟수 차트를 그린다                  |

## 7. 검증과 오류 처리

### 입력값 검증

`validateActivity()` 한 곳에서 세 가지를 순서대로 확인하고, 첫 번째 실패 사유를 돌려준다.

| 항목    | 조건            | 안내 문구                     |
| ----- | ------------- | ------------------------- |
| 활동명   | 공백 제거 후 1자 이상 | `활동명을 입력해 주세요.`           |
| 날짜    | 오늘 이하         | `미래 날짜는 입력할 수 없습니다.`      |
| 참여 인원 | 1 이상의 정수      | `참여 인원은 1명 이상의 정수여야 합니다.` |

- 오류는 폼 아래에 인라인 텍스트로 표시한다
- 날짜 입력란에는 `max` 속성으로 오늘 날짜를 넣어 1차로 막고, 자바스크립트 검증으로 한 번 더 막는다

### 삭제 확인

브라우저 `confirm()`을 쓰지 않는다. 삭제 버튼을 누르면 해당 카드 안에서 `정말 삭제할까요? [삭제] [취소]` 로 바뀌는 인라인 방식으로 한다.

이유는 두 가지다.

1. `confirm()` 같은 브라우저 모달은 페이지 스크립트를 멈춰 세워 브라우저 자동화 테스트를 불가능하게 만든다. 이 프로젝트는 마지막에 실제 브라우저로 전 기능을 눌러 검증하고 스크린샷을 확보해야 한다
2. 화면 안에서 확인이 끝나므로 모바일에서도 흐름이 자연스럽다

### 그 밖의 오류

- `localStorage` 파싱에 실패하면 빈 배열로 넘어간다. 앱이 죽지 않는다
- Chart.js 로딩에 실패하면 차트 영역만 비우고 나머지 기능은 그대로 동작한다

## 8. 구현 순서

차트를 맨 마지막에 둔다. 8번에서 막혀도 1–7번이 필수 요건과 선택 기능 2개를 채운 완성품으로 남는다.

| #   | 작업                      | 커밋 메시지                    |
| --- | ----------------------- | ------------------------- |
| 1   | HTML 뼈대 + 기본 CSS        | `기본구조: 화면 뼈대와 스타일 작성`     |
| 2   | 활동 등록 + localStorage 저장 | `활동등록: 입력 폼과 저장 기능 구현`    |

| 4   | 입력값 검증 3종               | `입력검증: 필수값·미래날짜·인원 검증 추가` |
| 5   | 활동 삭제 (인라인 확인)          | `활동삭제: 확인 후 삭제 구현`        |
| 6   | 키워드 검색                  | `검색: 활동명·장소 검색 구현`        |
| 7   | 반응형                     | `반응형: 모바일 레이아웃 대응`        |

| 9   | README + 스크린샷           | `문서: README 작성`           |

커밋 9회로 제출 요건(5회 이상)을 넘긴다. 기능 하나가 동작할 때마다 바로 커밋하고, 마지막에 몰아서 커밋하지 않는다.

## 11. 알려진 한계

- 데이터가 브라우저 localStorage에만 있어 다른 기기나 브라우저에서는 보이지 않는다
- 활동 수정 기능이 없다. 잘못 입력하면 삭제 후 다시 등록해야 한다
- 활동이 아주 많아지면 목록을 전부 다시 그리므로 느려질 수 있다. 이번 규모에서는 문제되지 않는다
