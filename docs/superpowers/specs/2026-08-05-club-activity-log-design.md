# 동아리 활동 기록 관리 웹앱 — 구현 계획

## Context

2026-08-05 해커톤 과제다. 요구사항은 `https://github.com/sung2ne/20260805` 의 명세서 3종에서 나왔다.

동아리 임원이 활동 내역을 등록·조회·삭제하는 웹앱을 서버 없이 만든다. 팀은 1팀 "끝맺음", 팀원은 이봉운 1명이다. 구현 가능 시간은 **14:00–16:10, 130분**이고 **16:40 이후 커밋은 인정되지 않는다.**

차별화 요소는 **주간 활동 리캡 영상**이다. 활동 1건을 이미지 1장으로 만들고, 한 주치를 묶어 30초짜리 영상 파일 하나로 뽑는다. 원래 구상은 로컬 AI 모델로 이미지를 생성하는 것이었으나, 명세가 "별도 서버·DB 불필요"를 요구하고 제출물은 강사가 클론해 열어보는 GitHub 저장소라서 로컬 모델은 채점 환경에서 동작하지 않는다. **파이프라인과 결과물은 그대로 두고 이미지 생성 주체만 `canvas` 렌더링으로 바꾼다.** 외부 라이브러리도 서버도 필요 없고 어느 PC에서든 동작한다.

선택 기능은 **검색 / 반응형 / 주간 리캡 영상** 3개다. 원래 넣으려던 월별 통계 차트는 뺐다. 영상과 역할이 겹치고, Chart.js를 빼면 외부 의존성이 0이 되며, 다른 팀과 겹치지 않는 쪽에 시간을 몰아주기 위해서다.

## 제품 톤 — 기록 도구가 아니라 회상 도구

동아리는 꿈이라는 하나의 뜻으로 묶인 사람들이다. 이 앱은 **행정 기록물이 아니라 나중에 다시 보며 즐거운 것**이어야 한다. 딱딱한 보고서 정리 앱과 갈라지는 지점이 여기다. 톤은 코드 비용이 거의 들지 않으므로 처음부터 넣는다.

이 방향이 구체적으로 바꾸는 것:

| 항목 | 기록 도구라면 | 이 앱은 |
|---|---|---|
| 화면 제목 | 활동 기록 관리 | **우리가 함께한 날들** (부제로 과제명 표기) |
| 목록 형태 | 표 형태의 행 나열 | **세로 타임라인** — 날짜 축을 따라 카드가 흐른다 |
| 리캡 영상 | 부가 기능 | **앱의 주인공.** 화면 상단에 배치하고 가장 크게 다룬다 |
| 빈 상태 | `아직 등록된 활동이 없습니다.` | `아직 기록된 날이 없어요.` / `첫 번째 이야기를 남겨보세요.` |
| 저장 버튼 | 저장 | **이 날 기록하기** |
| 삭제 확인 | 정말 삭제하시겠습니까? | `이 날의 기록을 지울까요?` `[지우기] [그대로 두기]` |
| 인원 표시 | 24 | `24명이 함께함` |
| 색 | 무채색 | **하늘** — 아래 비주얼 컨셉 참조 |

주의: 톤은 문구와 색까지다. 필수 요건(빈 목록 안내, 삭제 전 확인, 검증 오류 안내)은 문구만 바뀌고 동작은 명세 그대로 지킨다.

## 비주얼 컨셉 — 평원 위 구름 많은 맑은 하늘

**활동 1건 = 하늘 한 장.** 화면과 영상이 같은 세계관을 공유한다.

### 색 규칙

활동명 해시로 hue를 정하되 **하늘 팔레트 범위 안에서만** 움직인다. 그래서 어떤 활동은 이른 아침 하늘, 어떤 활동은 한낮, 어떤 활동은 노을이 된다. 영상에서는 하늘이 계속 바뀌며 흘러가는 그림이 된다.

| 요소 | 값 |
|---|---|
| 하늘 위 | `hsl(H, 65%, 62%)` |
| 하늘 아래 | `hsl(H, 70%, 86%)` |
| 구름 | `rgba(255,255,255,0.85~0.95)` |
| 앞 언덕 | `hsl(H-160, 40%, 45%)` |
| 뒤 언덕 | `hsl(H-160, 35%, 62%)` |
| 글자 | 흰색 + 옅은 그림자 |

`H` 는 `hashCode(title) % 360` 를 하늘 범위(대략 20°–260°)로 매핑해 얻는다. 같은 활동은 언제 봐도 같은 하늘이다.

### 화면 적용

- 페이지 배경 = 하늘 그라데이션 + 떠 있는 구름 (CSS)
- 타임라인 카드 = **구름처럼 둥근 흰 카드** (`border-radius` 크게, 부드러운 그림자)
- 카드 왼쪽에 그 활동의 하늘색 띠 → 영상에 나올 색을 미리 보여준다
- 페이지 하단에 언덕 실루엣 고정

### 구현 비용

구름은 원 5~8개 겹치기(`arc` + `fill`), 언덕은 `quadraticCurveTo` 2~3개다. 그라데이션은 `createLinearGradient` 한 줄. 저렴하다.

완료 시점의 목표 상태: 공개 GitHub 저장소에 동작하는 웹앱 + `CLAUDE.md` + `README.md`(스크린샷 2장 이상)가 올라가 있고, 커밋이 기능 단위로 10회 이상 쪼개져 있으며, 보고서 PDF 재료(계획 화면 캡처, 프롬프트 3건, 개선 사례 1건, 오류 해결 사례 1건, 테스트 결과)가 모두 확보된 상태.

### 검증 규칙 (4단계)

`validateActivity()` 한 곳에서 순서대로 확인하고 첫 실패 사유를 반환한다. 오류는 폼 아래 인라인 텍스트로 표시한다.

| 항목 | 조건 | 문구 |
|---|---|---|
| 활동명 | 공백 제거 후 1자 이상 | `활동명을 입력해 주세요.` |
| 날짜 | 오늘 이하 | `미래 날짜는 입력할 수 없습니다.` |
| 인원 | 1 이상 정수 | `참여 인원은 1명 이상의 정수여야 합니다.` |

날짜 입력란에 `max="오늘"` 을 넣어 1차로 막고, JS로 한 번 더 막는다.

### 삭제 확인 (5단계)

`confirm()` 을 쓰지 않는다. 삭제 버튼을 누르면 그 카드 안에서 `정말 삭제할까요? [삭제] [취소]` 로 바뀐다. 브라우저 모달은 페이지를 멈춰 세워 마지막 브라우저 자동 검증과 스크린샷 확보를 막기 때문이다.

### 주간 리캡 영상 (8–9단계) — 핵심 차별화

**파이프라인**

```
활동 1건 ──> 이미지 프레임 1장 ─┐
활동 1건 ──> 이미지 프레임 1장 ─┼─> 주차별 묶음 ─> canvas 애니메이션
활동 1건 ──> 이미지 프레임 1장 ─┘                        │
                                    canvas.captureStream(30fps)
                                                          │
                                        MediaRecorder ─> Blob ─> 다운로드
                                                          │
                                            recap-2026-W32.webm
```

**프레임 구성** (1280×720)

| 구간 | 길이 | 내용 |
|---|---|---|
| 표지 | 3초 | `8월 첫째 주` / `우리가 함께한 3일` |
| 활동 카드 | 활동당 4초 | 활동명(대), 날짜, 장소, `24명이 함께함`, 메모 첫 줄 |
| 마무리 | 3초 | `이번 주, 62명이 함께했어요` / `다음 주에도 만나요` |

문구는 통계 보고가 아니라 회상의 어조로 쓴다. 카드 배경색은 목록 화면의 그 활동 카드 색과 동일하다.

- 활동 3건이면 18초, 6건이면 30초. **활동 수에 비례해 길이가 정해진다** (30초는 6건 기준)
- 각 활동 카드의 배경은 **활동명 문자열 해시로 색상(hue)을 정한 그라데이션** — 활동마다 다른 그림처럼 보인다
- 프레임 전환은 페이드 인/아웃

**녹화**

- `canvas.captureStream(30)` → `new MediaRecorder(stream, { mimeType: 'video/webm' })`
- `requestAnimationFrame` 루프로 경과 시간을 계산해 해당 시점 프레임을 그린다
- 실시간 녹화라 영상 길이만큼 기다려야 하므로 **진행률 표시** 필수 (`영상 만드는 중... 12초 / 18초`)
- 끝나면 `Blob` → `URL.createObjectURL` → `<a download>` 자동 클릭
- **`MediaRecorder` 미지원 브라우저 가드**: 지원 안 하면 버튼을 감추고 안내 문구 표시. 나머지 기능은 정상 동작해야 한다

## 로컬 AI 모델 건 (보류, 폐기 아님)

명세에 로컬 모델을 **금지하는 조항은 없다.** 명세는 "별도 서버·DB 불필요"라고 썼을 뿐이고, "담당 교수 판단에 따라 기술 스택은 수업에서 다룬 것으로 대체할 수 있다"는 재량 조항도 있다. 보류하는 실제 이유는 두 가지다.

1. **재현성** — 제출물은 저장소 URL이고 강사가 클론해 연다. 강사 PC에 모델이 없으면 그 기능은 동작하지 않는다
2. **시간** — 남은 구현 시간이 부족하다. 로컬 파이프라인은 그 자체로 반나절 규모다

따라서: 본 제출물은 canvas로 완주한다. 시간이 남으면 `experiments/` 에 로컬 모델 버전을 붙이고, 안 되면 보고서 5장 "시간이 더 있었다면"에 판단 과정을 쓴다. 어느 쪽이든 재료가 된다.
