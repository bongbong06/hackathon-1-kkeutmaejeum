# 동아리 활동 기록 관리 웹앱 — 설계 문서

- 작성일: 2026-08-05
- 팀: 1팀 / 끝맺음
- 팀원: 이봉운 (1인 팀)

## 1. 목적과 범위

동아리 임원이 동아리 활동 내역을 등록하고, 목록으로 확인하고, 삭제할 수 있는 웹앱을 만든다.
서버 없이 브라우저 localStorage만으로 동작하며, 파일 3개(`index.html` / `style.css` / `app.js`)로 구성한다.

구현 시간은 130분(14:00–16:10)이다. 이 제약이 아래 모든 결정의 기준이다.

### 만들려는 것

동아리는 꿈이라는 하나의 뜻으로 묶인 사람들이다. 이 앱은 행정 기록물이 아니라 **나중에 다시 보며 즐거운 것**을 목표로 한다. 그래서 목록은 표가 아니라 타임라인이고, 앱의 주인공은 활동 목록이 아니라 **주간 리캡 영상**이다.

### 구현 범위

필수 기능 (전 팀 공통)

1. 활동 등록 — 활동명, 날짜, 장소, 참여 인원, 메모
2. 활동 목록 조회 — 최신순 정렬, 빈 목록일 때 안내 문구
3. 활동 삭제 — 삭제 전 확인 절차

입력값 검증

- 활동명은 필수. 비어 있으면 저장하지 않는다
- 날짜는 미래 날짜를 입력할 수 없다
- 참여 인원은 1 이상의 정수

선택 기능 (3개)

1. 활동명·장소 키워드 검색
2. 반응형 레이아웃 (모바일 대응)
3. 주간 리캡 영상 — 활동 1건을 canvas 이미지 프레임 1장으로 만들고, 한 주치를 묶어 webm 영상 파일로 저장

### 범위에서 제외

- 서버, 데이터베이스, 빌드 도구
- 로그인 및 사용자 구분
- 활동 수정, 기간 필터, JSON 내보내기/가져오기, 월별 통계 차트 — 시간 제약으로 제외
  - 차트는 리캡 영상과 역할이 겹치고, 빼면 외부 의존성이 0이 되어 제외했다

## 2. 기술 스택

- HTML / CSS / JavaScript (프레임워크 없음)
- 저장소: 브라우저 localStorage
- 외부 라이브러리: 없음

선택 기능 3번(주간 리캡 영상)은 브라우저 내장 API인 `canvas`, `canvas.captureStream()`, `MediaRecorder`만 쓴다. 설치할 것도 CDN에서 받을 것도 없다.

원래는 로컬 AI 이미지 생성 모델로 활동 이미지를 만들 계획이었다. 명세에 이를 금지하는 조항은 없고 "담당 교수 판단에 따라 기술 스택은 대체할 수 있다"는 재량 조항도 있으나, 제출물이 강사가 클론해 여는 GitHub 저장소여서 모델과 로컬 서버가 없는 환경에서는 해당 기능이 동작하지 않는다. 파이프라인(활동 → 이미지 → 주간 영상)과 결과물은 그대로 두고 이미지 생성 주체만 canvas 렌더링으로 바꿨다.

## 3. 비주얼 컨셉 — 평원 위 구름 많은 맑은 하늘

**활동 1건 = 하늘 한 장.** 화면과 영상이 같은 세계관을 공유한다.

```
+------------------------------------------+
|  .  ~            ~~                      |  하늘 그라데이션
|         ~~~                      ~       |  (위 진한 하늘 -> 아래 연한)
|   2026. 03. 02  금요일                    |
|                             ~~            |  구름: 원 여러 개를 겹쳐 그림
|   신입생 환영회                            |  배치·크기·개수는 활동명 해시로 결정
|   ---------                              |  -> 활동마다 다른 하늘 풍경
|   학생회관 대강당 · 24명이 함께함           |
|                                          |
|  /------\        /--------\              |  평원: 곡선 언덕 2겹
| /        \______/          \_____________|
+------------------------------------------+
```

### 색 규칙

활동명 해시로 색조(H)를 정하되 **하늘 팔레트 범위(20°–260°) 안에서만** 움직인다. 어떤 활동은 이른 아침 하늘, 어떤 활동은 한낮, 어떤 활동은 노을이 된다. 영상에서는 하늘이 계속 바뀌며 흘러가는 그림이 된다. 같은 활동은 언제 봐도 같은 하늘이다.

| 요소 | 값 |
|---|---|
| 하늘 위 | `hsl(H, 65%, 62%)` |
| 하늘 아래 | `hsl(H, 70%, 86%)` |
| 구름 | `rgba(255,255,255,0.85~0.95)` |
| 앞 언덕 | `hsl(H-160, 40%, 45%)` |
| 뒤 언덕 | `hsl(H-160, 35%, 62%)` |
| 글자 | 흰색 + 옅은 그림자 |

### 문구

행정 기록이 아니라 회상의 어조로 쓴다. 다만 문구만 바뀌고 명세가 요구하는 동작은 그대로 지킨다.

| 자리 | 문구 |
|---|---|
| 화면 제목 | 우리가 함께한 날들 |
| 저장 버튼 | 이 날 기록하기 |
| 빈 상태 | 아직 기록된 날이 없어요. / 첫 번째 이야기를 남겨보세요. |
| 검색 결과 없음 | 그런 날은 아직 없네요. |
| 삭제 확인 | 이 날의 기록을 지울까요? [지우기] [그대로 두기] |
| 인원 표시 | 24명이 함께함 |

## 4. 화면 구성

단일 페이지다. 데스크톱은 좌우 2단, 모바일은 1단으로 쌓인다.

```
[ 데스크톱 (>= 768px) ]                   [ 모바일 (< 768px) ]
+----------------------------------+     +--------------+
|      우리가 함께한 날들             |     |  헤더         |
+-------------+--------------------+     +--------------+
| 이 날 기록   |  [주간 리캡 영상]    |     | 리캡 영상     |
| 활동명 *    | 8월 첫째 주 3일       |     +--------------+
| 날짜   *    | [영상으로 보기]       |     | 기록 폼       |
| 장소        +--------------------+     +--------------+
| 인원   *    |  [검색어 입력]       |     | 검색바        |
| 메모        | ------------------ |     +--------------+
| [이 날      |  함께한 날 3일        |     | 타임라인      |
|  기록하기]  | +----------------+ |     +--------------+
+-------------+ | | 신입생 환영회  | |
| (언덕 실루엣) | | | 2026-03-02    | |
+-------------+-+----------------+-+
                  ^ 왼쪽 색 띠 = 그 활동의 하늘색
```

- 페이지 배경은 하늘 그라데이션, 카드는 구름처럼 둥근 흰 카드
- 빈 목록일 때와 검색 결과가 없을 때의 문구를 구분한다 (위 문구 표 참조)
- 목록 상단에 현재 표시 중인 활동 건수를 보여준다

## 5. 데이터 구조

`localStorage["activities"]`가 유일한 진실 소스다. 화면은 항상 여기서 다시 그린다.

활동 1건:

```js
{
  id,           // string. 고유 식별자
  title,        // string. 활동명 (필수)
  date,         // string. "YYYY-MM-DD"
  place,        // string. 장소
  memberCount,  // number. 참여 인원 (1 이상 정수)
  memo,         // string. 메모
  createdAt     // string. 등록 시각 ISO 문자열
}
```

- 배열 전체를 JSON 문자열로 직렬화해 한 번에 저장한다
- 정렬은 저장 시점이 아니라 화면에 그릴 때 `date` 기준 내림차순으로 한다

## 6. 데이터 흐름

단방향 흐름 하나로 통일한다.

```
사용자 입력
   -> activities 배열 변경
   -> saveActivities()
   -> render()
        +- renderList()          (검색어 필터 적용, 최신순 정렬)
        +- renderWeekSelector()  (주차별 묶음)
```

등록·삭제·검색 어디서든 `render()` 하나만 호출한다. 목록과 주차 선택기가 항상 같은 데이터를 보게 되므로 화면이 서로 어긋날 수 없다.

화면 상태는 두 가지뿐이다.

- `activities` — 활동 배열 (localStorage에서 읽어온 것)
- `searchKeyword` — 현재 검색어 (저장하지 않는다)

## 8. 검증과 오류 처리

### 입력값 검증

`validateActivity()` 한 곳에서 세 가지를 순서대로 확인하고, 첫 번째 실패 사유를 돌려준다.

| 항목 | 조건 | 안내 문구 |
|---|---|---|
| 활동명 | 공백 제거 후 1자 이상 | `활동명을 입력해 주세요.` |
| 날짜 | 오늘 이하 | `미래 날짜는 입력할 수 없습니다.` |
| 참여 인원 | 1 이상의 정수 | `참여 인원은 1명 이상의 정수여야 합니다.` |

- 오류는 폼 아래에 인라인 텍스트로 표시한다
- 날짜 입력란에는 `max` 속성으로 오늘 날짜를 넣어 1차로 막고, 자바스크립트 검증으로 한 번 더 막는다

### 삭제 확인

브라우저 `confirm()`을 쓰지 않는다. 삭제 버튼을 누르면 해당 카드 안에서 `이 날의 기록을 지울까요? [지우기] [그대로 두기]` 로 바뀌는 인라인 방식으로 한다.

이유는 두 가지다.

1. `confirm()` 같은 브라우저 모달은 페이지 스크립트를 멈춰 세워 브라우저 자동화 테스트를 불가능하게 만든다. 이 프로젝트는 마지막에 실제 브라우저로 전 기능을 눌러 검증하고 스크린샷을 확보해야 한다
2. 화면 안에서 확인이 끝나므로 모바일에서도 흐름이 자연스럽다

### 그 밖의 오류

- `localStorage` 파싱에 실패하면 빈 배열로 넘어간다. 앱이 죽지 않는다
- `MediaRecorder`를 지원하지 않는 브라우저에서는 영상 버튼을 감추고 안내 문구를 띄운다. 나머지 기능은 그대로 동작한다

## 9. 주간 리캡 영상

### 파이프라인

```
활동 1건 --> 이미지 프레임 1장 -+
활동 1건 --> 이미지 프레임 1장 -+-> 주차별 묶음 -> canvas 애니메이션
활동 1건 --> 이미지 프레임 1장 -+                        |
                                    canvas.captureStream(30fps)
                                                         |
                                       MediaRecorder -> Blob -> 다운로드
                                                         |
                                           recap-2026-W32.webm
```

### 프레임 구성 (1280×720)

| 구간 | 길이 | 내용 |
|---|---|---|
| 표지 | 3초 | `8월 첫째 주` / `우리가 함께한 3일` |
| 활동 카드 | 활동당 4초 | 활동명(대), 날짜, 장소, `24명이 함께함`, 메모 첫 줄 |
| 마무리 | 3초 | `이번 주, 62명이 함께했어요` / `다음 주에도 만나요` |

- 활동 3건이면 18초, 6건이면 30초. 활동 수에 비례해 길이가 정해진다
- 프레임 전환은 페이드 인/아웃
- 카드 배경색은 목록 화면의 그 활동 카드 색과 동일하다

### 녹화

- `canvas.captureStream(30)` → `new MediaRecorder(stream, { mimeType: 'video/webm' })`
- `requestAnimationFrame` 루프로 경과 시간을 계산해 해당 시점 프레임을 그린다
- 실시간 녹화라 영상 길이만큼 기다려야 하므로 진행률을 표시한다 (`영상 만드는 중... 12초 / 18초`)
- 끝나면 `Blob` → `URL.createObjectURL` → `<a download>` 자동 클릭

## 10. 구현 순서

각 단계는 동작 확인 후 바로 커밋한다. 마지막에 몰아서 커밋하지 않는다.

| # | 작업 | 커밋 메시지 |
|---|---|---|
| 1 | HTML 뼈대 + 기본 CSS | `기본구조: 화면 뼈대와 스타일 작성` |
| 2 | 활동 등록 + localStorage 저장 | `활동등록: 입력 폼과 저장 기능 구현` |
| 3 | 타임라인 조회 (최신순, 빈 상태 안내) | `활동목록: 최신순 타임라인 조회 구현` |
| 4 | 입력값 검증 3종 | `입력검증: 필수값·미래날짜·인원 검증 추가` |
| 5 | 활동 삭제 (인라인 확인) | `활동삭제: 확인 후 삭제 구현` |
| 6 | 키워드 검색 | `검색: 활동명·장소 검색 구현` |
| 7 | 반응형 | `반응형: 모바일 레이아웃 대응` |
| 8 | 리캡 — 주차 그룹핑 + 프레임 렌더링 | `리캡: 활동을 이미지 프레임으로 렌더링` |
| 9 | 리캡 — 영상 녹화·다운로드 | `리캡: 주간 영상 생성 및 다운로드 구현` |
| 10 | README + 스크린샷 | `문서: README 작성` |

리캡 영상(8–9)이 가장 무겁고 불확실해서 맨 마지막에 둔다. 여기서 막혀도 1–7이 필수 요건과 선택 기능 2개를 채운 완성품으로 남는다. 16:00까지 9단계가 안 끝나면 중단하고 10단계로 넘어간다.

## 13. 알려진 한계

- 데이터가 브라우저 localStorage에만 있어 다른 기기나 브라우저에서는 보이지 않는다
- 활동 수정 기능이 없다. 잘못 입력하면 삭제 후 다시 등록해야 한다
- 리캡 영상의 이미지는 canvas로 그린 것이라 사진 같은 그림은 나오지 않는다. 타이포그래피와 색, 도형으로 구성된 포스터 형태다
- 영상 녹화가 실시간이라 영상 길이만큼 기다려야 한다
- 활동이 아주 많아지면 목록을 전부 다시 그리므로 느려질 수 있다. 이번 규모에서는 문제되지 않는다
